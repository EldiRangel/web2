PRUEBAS DE SECURITY EN POSTMAN (NAVEGADOR)
Proyecto: Express Session
Base URL: http://localhost:3000

======================================================================
0. ANTES DE EMPEZAR
======================================================================

1. Abrir una terminal en:

   C:\Users\Eldi\Desktop\Web2\Express Session

2. Iniciar el servidor:

   npm start

   Debe quedar escuchando en http://localhost:3000

3. Si la base de datos es nueva o no tiene los datos demo:

   npm run db:setup

   Si ya probaste antes y la base demo existe, NO hace falta ejecutarlo.

4. Crear en Postman una coleccion llamada:

   Nomina - Security

5. En cada peticion POST:

   - Ir a la pestana Body.
   - Seleccionar raw.
   - Seleccionar JSON en el desplegable.
   - Pegar el body indicado.
   - Verificar que el header Content-Type sea application/json.

6. Postman guarda las cookies de sesion automaticamente.
   Se pueden ver en el enlace "Cookies", debajo del boton Send.

7. IMPORTANTE:
   El login NO cambia de usuario si ya hay una sesion activa.
   Si intentas entrar como Bruno sin cerrar la sesion de Ana, el servidor
   responde "Sesion ya activa" y sigues siendo Ana.

   Por eso, antes de cambiar de usuario:
   - Enviar POST /api/auth/logout, o
   - Borrar la cookie "sid" desde Cookies.

8. Usar siempre el mismo host:
   - http://localhost:3000
   o
   - http://127.0.0.1:3000

   No mezclarlos, porque las cookies se guardan por dominio.

9. Si usas Postman Web (el del navegador) y localhost no responde:
   - Instalar Postman Desktop Agent.
   - Seleccionarlo en la parte inferior derecha de Postman.
   - Si sigue fallando, usar la aplicacion de escritorio de Postman,
     que es mas estable para probar localhost y sesiones.

10. MODO SIN BUSINESS (estado actual del proyecto):
   La carpeta server/src/business no existe todavia. El servidor arranca
   igualmente y registra las operaciones en modo PENDIENTE.

   Las operaciones autorizadas devuelven 200 con un body parecido a:

   {
     "success": true,
     "data": {
       "pendiente": true,
       "operacion": "Empleados.listar",
       "mensaje": "La capa business no esta implementada todavia."
     }
   }

   Eso es CORRECTO para esta etapa: sirve para probar login, sesion,
   permisos, 401, 403, 400 y 404. No devuelve empleados reales ni calcula
   nomina. Cuando se restaure la capa business, las mismas peticiones
   ejecutaran la logica real.

4. PRUEBA CLAVE: REVOCACION DE PERMISO EN CALIENTE
======================================================================

Esta prueba demuestra que Security consulta PostgreSQL en cada peticion
y que no basta con tener una sesion abierta o un mapa en memoria.

----------------------------------------------------------------------
4.1 Preparacion
----------------------------------------------------------------------

1. Iniciar sesion como Bruno.
2. Confirmar que Bruno puede listar empleados con Empleados.listar
   (la peticion 2.6 debe dar 200).
3. No cerrar sesion.
4. No reiniciar el servidor.

----------------------------------------------------------------------
4.2 Comprobar el permiso actual
----------------------------------------------------------------------

Abrir pgAdmin o psql, conectarse a la misma base del proyecto y ejecutar:

SELECT pm.allowed
FROM permission_method pm
JOIN profiles p ON p.id = pm.profile_id
WHERE p.name = 'editor'
  AND pm.subsystem_id = 1
  AND pm.class_id = 1
  AND pm.method_id = 2;

Resultado esperado: true

----------------------------------------------------------------------
4.3 Revocar Empleados.listar al perfil editor
----------------------------------------------------------------------

Ejecutar:

UPDATE permission_method
SET allowed = FALSE,
    updated_at = NOW()
WHERE subsystem_id = 1
  AND class_id = 1
  AND method_id = 2
  AND profile_id = (
      SELECT id
      FROM profiles
      WHERE name = 'editor'
  );

Verificar otra vez con el SELECT de 4.2.
Ahora debe devolver false.

----------------------------------------------------------------------
4.4 Repetir la peticion de Bruno SIN volver a hacer login
----------------------------------------------------------------------

Metodo: POST
URL:    http://localhost:3000/api/dispatcher
Body:   raw / JSON

{
  "subsystemId": 1,
  "classId": 1,
  "methodId": 2,
  "params": {}
}

Resultado esperado: 403 Forbidden

Debe pasar de 200 a 403 sin reiniciar el servidor y sin cerrar sesion.

----------------------------------------------------------------------
4.5 Probar con Ana y comprobar la denegacion prevalente
----------------------------------------------------------------------

Sin cerrar la sesion de Bruno, iniciar sesion como Ana no es posible
si no se cierra la sesion. Para esta prueba:

1. Cerrar la sesion de Bruno.
2. Iniciar sesion como Ana.
3. Enviar la misma peticion de Empleados.listar.

Resultado esperado: 403 Forbidden

Ana tiene admin y editor. El permiso admin sigue en true, pero el permiso
editor ahora esta en false. La denegacion explicita prevalece.

----------------------------------------------------------------------
4.6 Restaurar el permiso
----------------------------------------------------------------------

Ejecutar:

UPDATE permission_method
SET allowed = TRUE,
    updated_at = NOW()
WHERE subsystem_id = 1
  AND class_id = 1
  AND method_id = 2
  AND profile_id = (
      SELECT id
      FROM profiles
      WHERE name = 'editor'
  );

Verificar con el SELECT de 4.2: debe volver a true.

Enviar otra vez la peticion de Empleados.listar con Ana o Bruno.
Resultado esperado: 200 OK.

6. CONSULTAS SQL DE APOYO
======================================================================

----------------------------------------------------------------------
6.1 Ver usuarios y perfiles
----------------------------------------------------------------------

SELECT u.email,
       p.name AS perfil,
       up.active AS asignacion_activa,
       u.active AS usuario_activo,
       pe.active AS persona_activa
FROM users u
JOIN user_profiles up ON up.user_id = u.id
JOIN profiles p ON p.id = up.profile_id
LEFT JOIN person pe ON pe.id = u.person_id
ORDER BY u.email, p.name;

Esperado:
  ana@example.com    admin
  ana@example.com    editor
  bruno@example.com  editor
  carla@example.com  viewer

----------------------------------------------------------------------
6.2 Ver IDs reales de las operaciones
----------------------------------------------------------------------

SELECT s.id AS subsystem_id,
       c.id AS class_id,
       m.id AS method_id,
       c.name AS clase,
       m.name AS metodo
FROM subsystem s
JOIN "class" c ON c.subsystem_id = s.id
JOIN method m ON m.class_id = c.id
WHERE s.name = 'Nomina'
ORDER BY c.name, m.name;

Usar estos IDs en las peticiones si son distintos de los indicados arriba.

----------------------------------------------------------------------
6.3 Ver la matriz de permisos
----------------------------------------------------------------------

SELECT p.name AS perfil,
       s.name AS subsistema,
       c.name AS clase,
       m.name AS metodo,
       pm.allowed
FROM permission_method pm
JOIN profiles p ON p.id = pm.profile_id
JOIN subsystem s ON s.id = pm.subsystem_id
JOIN "class" c ON c.id = pm.class_id
              AND c.subsystem_id = pm.subsystem_id
JOIN method m ON m.id = pm.method_id
             AND m.class_id = pm.class_id
WHERE s.name = 'Nomina'
ORDER BY p.name, c.name, m.name;

Permisos demo esperados:
  admin  -> todas las operaciones en true
  editor -> consultas, empleados, salarios, bonos, horas extras,
            prestamos, calcular/consultar prenomina; NO cerrar nomina
  viewer -> Empleados.listar, Empleados.consultar,
            Salarios.consultar, Prenomina.consultar,
            NominaDefinitiva.consultar

8. PROBLEMAS COMUNES
======================================================================

1. "Sesion ya activa"
   No cerraste la sesion del usuario anterior.
   Enviar POST /api/auth/logout y volver a hacer login.

2. Esperabas 403 y recibiste 200
   Probablemente no estas logueado con el usuario correcto.
   Ejecutar GET /api/auth/session.

3. Recibes 404
   Los subsystemId, classId o methodId no son los correctos.
   Ejecutar la consulta 6.2.

4. Recibes 401 al hacer login
   Revisar email y password.
   Revisar que el seed se haya ejecutado.

5. Postman Web no conecta con localhost
   Instalar y seleccionar Postman Desktop Agent.
   O usar la aplicacion de escritorio de Postman.

6. Error de CORS en Postman Web
   Usar Desktop Agent o la aplicacion de escritorio.

7. Las cookies no se guardan
   Verificar que siempre usas el mismo host y puerto.
   No mezclar localhost con 127.0.0.1.

8. El servidor no responde
   Verificar que npm start sigue ejecutandose.
   Verificar que el puerto sea 3000.

9. Error 500
   Revisar la consola donde corre npm start.
   El cliente no debe recibir el detalle interno del error.

10. Recibes 200 con "pendiente": true
   Es el modo sin business. El permiso y la sesion funcionaron, pero la
   logica de nomina todavia no esta instalada. Es lo esperado en esta etapa.
